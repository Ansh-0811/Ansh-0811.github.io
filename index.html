YoCam

AI dashcam and driver safety system. Independent project, 2026.

YoCam is working and tested on real hardware. It is installed in a car on a Raspberry Pi 5 with a custom HAT board that I designed and assembled, and it reads live vehicle data over OBD-II.

It records video, runs AI models on the device to watch the road and the driver, detects crashes, and can place an emergency call through a paired phone. The rule I built it around: the recording must never stop because something else broke.

How the services work together

How it is built

  1. Video frames travel through shared memory, not the message bus.

    The recorder writes each camera frame into a ring of slots in shared memory, and the writer never waits for a reader. Each slot carries a sequence number that is odd while the slot is being written. A reader that catches a half-written frame sees the number change and reads again, so it never uses a torn frame.

  2. I hit a known CPython bug in shared memory and worked around it.

    A process that only attached to the shared memory would delete it when it exited, which destroyed the recorder's live buffer. I stopped attached processes from being tracked as owners, so only the owner can delete the memory, and the live previews reconnect by themselves after a recorder restart. CPython issue bpo-38119

  3. Every hardware driver also has a simulated version.

    In the car, the real drivers run. The camera, OBD-II, GPS, IMU and phone each also have a simulated driver behind the same interface, so the whole system runs end to end on a laptop. The automated tests run against the simulated drivers, and the real drivers are tested by running the system in the car.

  4. A failed service does not take the rest down.

    The services are started so that one stopping leaves the others running, and the system reports a degraded state and carries on.

  5. Calibration is a state machine.

    Setup walks through steering, throttle, brake, the IMU and the cameras as explicit steps. Each step ends in one of four outcomes (success, retry, motion abort or fatal) and has a retry limit. If the car moves during setup, calibration stops and keeps what it has measured so far.

Rakshak

Android-first safety app for India's gig delivery riders and drivers.

Rakshak shares your shift location with a trusted crew automatically, checks on you if you stop too long, and sends a one-tap SOS.

This is Launch Base, the first of three planned releases.

Status

Backend

How an SOS gets out

How it is built

  1. An automatic shift start keeps location on the phone until it is confirmed.

    When a shift starts automatically, the location stays on the phone. Nothing is shared until the shift is confirmed, and Undo erases what was held.

  2. One upload call is also the heartbeat.

    A single idempotent call carries the batched location and doubles as the heartbeat. GPS adapts, every 15 seconds while moving and every 60 seconds while stationary, so the radio can sleep.

  3. The crew map polls instead of holding sockets open.

    The map polls every 25 seconds. That is a deliberate cost choice over realtime sockets.

  4. Privacy is enforced in the database and again at read time.

    Every table has row-level security. Read-time filters make a hidden member look the same as one who is off shift, and location is coarsened after 30 minutes and gone after 2 hours.

  5. Release builds fail closed.

    Fake data exists only in debug builds.

Tansh

Self-hosted media streaming server and app.

Tansh is a self-hosted media streaming server and app for my own media library, with profiles and a synchronized watch party.

Status
Working build
Stack

How each file reaches the player

How it is built

  1. A phone acting as the server throttles instead of overheating.

    Concurrency control is thermal-aware: as the device heats up, the server takes on less work at once. The control has hysteresis. Throttling starts at one temperature and lifts at a lower one, so it does not flip back and forth around a single point.

  2. The watch party has one host in charge.

    Everyone's playback stays in sync over Socket.IO. One viewer is the host and has authority over playback, and the host role can be transferred to another viewer.

  3. Each viewer has a profile.

    Profiles sit behind a PIN gate in the app.

18,429 lines of JS/JSX/CSS, 17 backend services.
